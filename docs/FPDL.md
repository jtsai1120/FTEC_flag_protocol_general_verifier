# FPDL — Flag Protocol Description Language

FPDL describes a quantum error-correcting code (QECC) flag protocol. A `.fpdl`
file has the following top-level form:

```fpdl
protocol <protocol_name>:
    code: ...
    se:   ...
    gvar: ...
    tc:   ...
    af:   ...
    tp:   ...
```

This document uses **parser** as shorthand for the complete FPDL front end. In
addition to parsing syntax, the front end performs type checking, control-flow
analysis, and the static validity checks described below.

## Static validity requirements

An FPDL protocol is valid only if the parser can establish all of the following:

1. The program is well typed.
2. No fixed-length vector is partially assigned.
3. The terminal conditions are mutually exclusive: no two distinct conditions
   `tc[i]` and `tc[j]` can be true in the same reachable program state.
4. Every possible execution path reaches a terminal condition after finitely
   many adaptive-flow rounds, and no internal loop can execute forever within a
   round. All possible syndrome and flag outcomes of an SE invocation must be
   considered when checking this property.
5. Every terminating-policy path terminates after finitely many steps.
6. No possible execution path reaches a runtime assertion error, including
   counter underflow, out-of-range indexing, invalid null use, vector-length
   mismatch, or a nonexhaustive `switch`.

### Bounded model checking

The parser performs these checks with bounded model checking (BMC). Every parser
invocation must supply a positive integer bound `B`; there is no default bound.
`B` is the maximum number of transition steps in a complete trace from the
initial state through termination of its selected `tp` entry. Executing one
statement, evaluating one control-flow guard, or taking one control-flow edge is
one transition; an atomic SE tuple assignment is one transition.

The parser explores every trace through depth `B`. It treats every SE result as
an arbitrary bit pattern compatible with that SE's declared return type. A
protocol passes at bound `B` only if the parser proves that:

- all traces have executed `decode()` or `end()` before depth `B` is exceeded;
- no assertion error is reachable at any explored depth; and
- all reachable terminal conditions are mutually exclusive.

If any trace is still live at depth `B`, or if any required property cannot be
proved, the parser rejects the protocol at that bound. Every verification report
must record `B`, because acceptance is relative to the supplied bound.

## `code` — QEC code

```fpdl
code:
    [[<n>, <k>, <d>]]                       # physical qubits, logical qubits, distance
    [[<g1>], [<g2>], ...]                   # stabilizer generators
```

A generator `<gi>` can be written in either of the following forms:

- **dense** — `[[I, X, X, Z], [Z, X, X, I], [I, Z, Z, Z]]`
- **sparse** — `[[X3, X4, X5, X6], [X14, X15, X16, X17], [Z1, Z2, Z3, Z4]]`

Sparse qubit indices are one-based, and omitted qubits represent `I`. Every
dense generator must contain exactly `n` Pauli operators. The parser must reject
out-of-range or repeated sparse indices, noncommuting generators, and a
generator set inconsistent with the declared `[[n,k,d]]` code.

An SE's `g` entry may contain any element of the `n`-qubit Pauli group; it need
not repeat one of the listed generators verbatim. The parser must prove that
measuring every listed Pauli has a deterministic outcome on the declared code
space. For an unsigned `+1` stabilizer-code description, this is equivalent to
membership in the stabilizer group generated by the `code` entries. A Pauli
whose measurement can distinguish logical code states is not deterministic and
must be rejected.

## `se` — syndrome-extraction circuits

```fpdl
se:
    <se_name> {
        file: <OpenQASM_file_path>
        qd: <data_qreg>
        qm: <measurement_qreg>
        qf: <flag_qreg>                     # required only for a flagged SE
        g:  <generator_set>                 # claimed measured generator(s)
        #-flag: <t>                         # required only for a flagged SE
    }
```

A relative `file` path is resolved relative to the directory containing the
`.fpdl` file.

Only quantum registers are declared. Where an outcome lands is not a separate
fact: `m[0] = measure syn;` in the QASM already binds a classical register to
the qubit it reads, so naming the syndrome and flag ancillas is enough for a
backend to find the syndrome and flag records. Declaring the classical
registers as well would let the two disagree, with the syndrome read silently
off the flag register.

An SE is a black-boxed, atomic operation when called from `af` or `tp`. Every SE
invocation returns a tuple:

```fpdl
(s,)   = unflagged_se();
(s, f) = flagged_se();
```

Here, the **return type** means the number and type of values returned by the
invocation. `s` has type `bit` for a one-bit syndrome and `bit[L]` for an
`L`-bit syndrome. Likewise, `f` has type `bit` or `bit[F]` according to the
width of the flag register. The parser obtains the register widths from the
referenced QASM file -- finding each register by which measurement writes to it
-- and checks that the tuple arity and destination types agree. The ordering
of tuple members is always syndrome first and flag second.

SE references may carry a return signature. For example:

```fpdl
se<(bit, bit[])>[16] gf = [g1f, g2f, ..., g16f];
```

This declares a fixed-length vector of 16 flagged SE references. Each SE must
return a scalar syndrome `bit`; its flag result may be a bit-vector of any
length. A fixed return such as `bit[1]` or `bit[3]` is compatible with the
`bit[]` return slot. SE references are compatible exactly when every return
component can be assigned to the corresponding component of the declared
signature.

SE calls are effectful because they execute a circuit. Consequently, an SE call
must appear in an explicit tuple assignment; it cannot be nested directly in
`push`, `decode`, a vector literal, or another expression.

### `#-flag`

`#-flag` does not denote the number of flag qubits. A circuit claimed to be a
`t`-flag circuit must have the following property: for every fault assignment
containing `v` faults, where `0 < v <= t`, a propagated error whose applicable
minimum weight is greater than `v` causes at least one flag outcome to be raised.

The precise circuit fault model and the equivalence relation used when taking
the minimum error weight are inputs to the verifier rather than properties of
the FPDL surface syntax. A verification result must identify both, so that the
meaning of the `#-flag` claim is unambiguous.

## `gvar` — global variables

Global variables represent adaptive-flow state or retain structured measurement
records.

```fpdl
gvar:
    <data_type> <var_name>;                 # initialized to ⊥
    <data_type> <var_name> = <init_value>;
```

Local variables use the same declaration syntax inside a block. A local
variable has block scope and is initialized each time execution enters its
declaration. Loop variables must be declared before use and may be modified.

### Scalar and record types

| Type | Domain | Meaning |
|---|---|---|
| `bit` | `{⊥, 0, 1}` | one classical bit |
| `cnt` | `{⊥, 0, 1, 2, ...}` | a nonnegative integer counter |
| `mr` | `{⊥}` plus heterogeneous structured records | a measurement record |
| `se<(T1,...)>` | `{⊥}` plus SE references with compatible return signatures | a syndrome-extraction circuit reference |

`⊥` is the null/unassigned value. It is one monolithic value; it is not a
vector whose individual elements are unassigned.

### Null semantics

- `⊥ == ⊥` evaluates to `true`.
- `⊥ != 0` evaluates to `true`.
- Equality and inequality comparisons involving `⊥` are permitted.
- An ordered comparison with the literal `⊥`, such as `⊥ > 0`, is a static
  error. If an operand of an otherwise valid ordered comparison evaluates to
  `⊥` at runtime, execution fails with an assertion error.
- An uninitialized variable may be tested with `==` or `!=` in a terminal
  condition or another Boolean expression.
- Any other operation that requires the underlying value of `⊥` is an error.

### Vector types

```fpdl
bit[3] fixed = [0, 1, 0];   # fixed length
bit[]  open  = [];          # arbitrary length
bit[][] rows = [];          # vector of arbitrary-length bit-vectors
se<(bit, bit[])>[] circuits = []; # flagged SEs with compatible signatures
```

A fixed-length vector is atomic with respect to assignment: it must be assigned
as a complete value and cannot be partially assigned. Indexed assignment to a
fixed-length vector is always forbidden, including after complete
initialization. In particular, both indexed assignments below are invalid:

```fpdl
bit[16] s = ⊥;
s[i] = si;                  # error: partial assignment

bit[4] initialized = [0, 0, 0, 0];
initialized[0] = 1;         # error: fixed-vector indexed update
```

Build a vector incrementally by using an initialized arbitrary-length vector:

```fpdl
bit[] s = [];
s.push(si);
```

The parser permits a fixed-length vector to be assigned to a compatible
arbitrary-length vector. Assignment in the other direction is not permitted.
Vector indexing is zero-based. Reading an out-of-range index causes an assertion
error; the parser must prove that such an error is unreachable.

`0` may denote an all-zero **bit-vector** of any length when the required length
is determined by the other operand or the destination type. This promotion does
not apply to vectors of `cnt`, `se`, `mr`, or any other element type. If the
required bit-vector length cannot be inferred, use an explicit vector literal.

Braces concatenate scalar bits and bit-vectors. A scalar bit is treated as a
length-one bit-vector for concatenation, and the result is one flat bit-vector:

```fpdl
bit[3] a = [0, 1, 0];
bit[3] b = [1, 0, 1];
bit[6] c = {a, b};
bit s = 0;
bit f = 1;
bit[2] sf = {s, f};
```

Tuple syntax is distinct: parentheses are used for SE return values, while
braces are used for vector concatenation.

### Measurement records

An `mr` is a heterogeneous ordered sequence. A measurement-record literal uses
the explicit `mr[...]` form:

```fpdl
mr empty = mr[];
mr one_round = mr[s_prev];
mr history = mr[m1, f1, m2, f2];
```

Ordinary `[...]` remains vector-literal syntax and never denotes an `mr`.
`push` appends one complete value as one record element and preserves that
element's type, length, and boundary.

For example, these two records are different:

```fpdl
mr[[0, 1], [1, 0]]
mr[0, 1, 1, 0]
```

The first contains two bit-vector elements; the second contains four bit
elements. In this document, an **element boundary** is the retained separation
between those top-level record elements. Records are not implicitly flattened.
`decode()` receives this structured record, including its element boundaries.

## `tc` — terminal conditions

```fpdl
tc:
    <tc_num>: <bool_expr>
```

The aggregate terminal predicate is defined as:

```text
tc ≡ tc[1] or tc[2] or ... or tc[N]
```

The parser must prove that the individual terminal conditions are mutually
exclusive over all reachable states. Therefore, whenever `tc` is true, exactly
one `tc[i]` is true and its corresponding `tp[i]` is selected.

Every `tc[i]` must have exactly one corresponding `tp[i]`, and a `tp` entry may
not exist without a corresponding terminal condition.

A terminal condition may reference only global variables declared in `gvar`,
literals, and pure expressions. It may not reference an `af` or `tp` local
variable, invoke an SE, mutate state, or perform any other side effect.

### Boolean expressions

A Boolean expression consists of:

- two compatible operands with `==` or `!=`;
- two compatible, non-null ordered values with `>`, `<`, `>=`, or `<=`;
- two Boolean expressions joined by `and` or `or`;
- the Boolean literals `true` and `false`.

The language does not currently provide a general unary `not` operator. For an
assigned scalar `bit`, `not x` would be equivalent to `x == 0`, so ordinary bit
and null tests can instead use `x == 0`, `x != 0`, `x == ⊥`, or `x != ⊥`.
These explicit comparisons also avoid giving an ambiguous meaning to `not ⊥`.
The token `!` in `while (!tc)` is reserved syntax for the negation of the
aggregate terminal predicate and is not a general operator.

## `af` — adaptive flow

```fpdl
af:
    while (!tc) {
        <execution>
    }
```

The outer `while (!tc)` is the adaptive-flow loop. One entry into its body is
one adaptive-flow round. The aggregate `tc` predicate is checked before every
round. If it is true, the body is not entered and the unique matching
terminating policy runs.

Use `check();` to request the same test in the middle of a round:

```fpdl
<execution>;
check();
<more_execution>;
```

If `tc` is false, execution continues with the next statement. If it is true,
the adaptive flow terminates immediately and the unique matching `tp` entry
runs. The parser includes every explicit `check()` point in its termination and
reachability analysis.

### Control flow

```fpdl
if (<bool_expr>) { <execution>; }
else if (<bool_expr>) { <execution>; }
else { <execution>; }

switch (<variable>) {
    <value1>: { <execution>; }
    <value2>: { <execution>; }
    default: { <execution>; }
}

while (<bool_expr>) { <execution>; }
```

FPDL does not have a `for` statement. A loop counter must be declared before a
`while` loop and explicitly updated inside it.

A `switch` never falls through. After executing the unique matching case, flow
automatically continues after the `switch`. If no case matches and there is no
`default`, execution fails with an assertion error; the parser must prove that
this error is unreachable.

`break` and `continue` have the same control-flow meaning as in C++:

- `break;` exits the nearest enclosing `while` or `switch`.
- `continue;` skips the remainder of the nearest enclosing `while` body and
  begins that loop's next condition test.

For an outer `while (!tc)`, `continue;` therefore proceeds to its implicit
terminal-condition check.

### Expressions and execution primitives

- `(s,) = g1();` — execute an unflagged SE and unpack its one-element result tuple.
- `(s, f) = g1f();` — execute a flagged SE and unpack its result tuple.
- `a = b;` — assign `b` to `a` when their types are compatible.
- `a++;` — add one to a `cnt`.
- `a += b;` — add one `cnt` to another.
- `a + b`, `a - b` — counter arithmetic.
- `a[i]` — read element `i` using zero-based indexing.
- `a.push(b);` — append `b` as one element of an arbitrary-length vector or
  measurement record.
- `check();`, `break;`, `continue;` — perform the control-flow actions described
  above.

Arithmetic on `cnt` is checked. If subtraction would produce a negative value,
execution fails with an assertion error. The parser must prove that underflow is
unreachable; otherwise it rejects the protocol.

Parentheses determine grouping. Otherwise, arithmetic operators bind more
tightly than comparison operators, which bind more tightly than `and`, which
binds more tightly than `or`.

## `tp` — terminating policy

```fpdl
tp:
    <tc_num>: { <terminate_execution>; }
```

A terminating policy may perform declarations, SE tuple assignments,
assignments, structured-record operations, and control flow. Every possible
terminating-policy path must itself finish within the BMC bound. `check()` is
valid only in `af` and is forbidden in `tp`.

The explicit terminal actions are:

- `decode(<lookup_record>);` — invoke an external LUT decoder; `<lookup_record>`
  must have type `mr`.
- `end();` — terminate without decoding.

Both are non-returning primitives. No reachable statement may follow either
one, and each `tp` path may execute at most one of them.

If control reaches the closing brace of a terminating policy without executing
`decode()` or `end()`, FPDL implicitly executes `end()`. Thus an empty policy is
equivalent to:

```fpdl
<tc_num>: {
    end();
}
```

The implicit `end()` is part of the transition system and consumes one BMC
transition, just like an explicit `end()`.

`decode()` is currently an external black box. FPDL preserves and passes the
complete structure of its argument; it does not flatten the measurement record.
